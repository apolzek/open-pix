# DICT API Reference

Reference documentation for the DICT (Diretorio de Identificadores de Contas Transacionais) API v2 used in Pix Direct Participant homologation with Bacen. It follows the official **DICT API 2.12.1** specification; a copy of its OpenAPI file lives in `simulator/spec/dict-2.12.1/openapi.json`. When in doubt, that file wins over this page.

DICT is the centralized directory that maps Pix keys to transactional accounts. All operations use XML over HTTPS with mTLS on the RSFN network.

---

## Overview

- **Base URL (homologation):** `https://dict-h.pi.rsfn.net.br:16522/api/v2/`
- **Base URL (production):** `https://dict.pi.rsfn.net.br:16422/api/v2/`
- **Authentication:** mTLS with the participant's RSFN certificate (Manual de Seguranca do Pix)
- **Content-Type:** `application/xml` (errors: `application/problem+xml`)
- **API version:** the path carries only the major version (`v2`). `v1` is the old version.
- **XML:** request and response roots have **no XML namespace** (`<CreateEntryRequest>`, `<GetEntryResponse>`, ...). `<Signature>` is the first child.
- **Signatures:** requests that create or change data must carry an enveloped XMLDSig in `<Signature>`. Queries (GET) are not signed. Every DICT response is signed and clients **must** verify the signature.
- **Compression:** the DICT does **not** accept compressed request bodies. Send `Accept-Encoding: gzip` to receive compressed responses.
- **Dates:** ISO 8601 date-times in UTC (`Z`), e.g. `2020-01-10T10:00:00.000Z`.
- **Connections:** reuse connections (keep-alive / connection pool); the mTLS handshake is expensive. The API returns a `Keep-Alive` header with a `timeout`.

In this toolkit, `DictClient.call(method, path, body?, { payerId, endToEndId, query, okStatus })` (in `scripts/utils/http-client.ts`) prefixes `path` with `/api/v2`, sets `PI-RequestingParticipant` to your ISPB and never compresses the request body. It does not sign; sign write requests before calling it.

```typescript
import { DictClient } from "./scripts/utils/http-client.js";

const dict = new DictClient({ baseUrl: "https://dict-h.pi.rsfn.net.br:16522", ispb: "12345678", certPath, keyPath, caPath });

// Lookup before a payment: PI-PayerId and PI-EndToEndId are mandatory
const res = await dict.call("GET", `/entries/${encodeURIComponent("+5561988887777")}`, undefined, {
  payerId: "11122233300",
  endToEndId: "E12345678202609281435abcDEF12345",
  okStatus: [404],
});
```

## Key Types

| Key Type | Format | Example | Can be claimed |
|----------|--------|---------|----------------|
| CPF | 11 digits | `11122233300` | Portability only |
| CNPJ | 14 digits | `11222333000150` | Portability only |
| PHONE | E.164 | `+5561988887777` | Portability and ownership |
| EMAIL | Email address (max 77 chars for any key) | `user@example.com` | Portability only |
| EVP | UUID v4, generated by the DICT (omit `<Key>` on creation) | `123e4567-e89b-12d3-a456-426614174000` | Neither |

The claim matrix above is the one in the `createClaim` operation of the API spec. The number of keys per account is limited; exceeding it returns `EntryLimitExceeded`. (The limit itself, commonly 5 keys per account for natural persons and 20 for legal entities, is set by the Pix regulation, not by the API spec.)

Account fields (`BrazilianAccount`): `Participant` (ISPB, `[0-9A-Z]{8}`), `Branch` (up to 4 digits, optional), `AccountNumber` (`[a-zA-Z0-9]{1,20}`), `AccountType` (`CACC`, `TRAN`, `SLRY`, `SVGS`, `OTHR`), `OpeningDate` (date-time; when the time is unknown, the spec convention is the start of the day in Brasilia time, e.g. `2010-01-10T03:00:00Z`).

Owner fields (`Person`): `Type` (`NATURAL_PERSON` or `LEGAL_PERSON`), `TaxIdNumber` (CPF or CNPJ), `Name`, and `TradeName` (legal persons, optional).

## Operations

### createEntry

Registers a new key, linking it to a transactional account. Idempotent through `RequestId` (UUID v4, unique per participant); reusing a `RequestId` with different parameters returns `RequestIdAlreadyUsed`. Valid `Reason` values: `USER_REQUESTED`, `RECONCILIATION`.

**Endpoint:** `POST /api/v2/entries/`

**Request:**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateEntryRequest>
    <Signature></Signature>
    <Entry>
        <Key>+5561988880000</Key>
        <KeyType>PHONE</KeyType>
        <Account>
            <Participant>12345678</Participant>
            <Branch>0001</Branch>
            <AccountNumber>0007654321</AccountNumber>
            <AccountType>CACC</AccountType>
            <OpeningDate>2010-01-10T03:00:00Z</OpeningDate>
        </Account>
        <Owner>
            <Type>NATURAL_PERSON</Type>
            <TaxIdNumber>11122233300</TaxIdNumber>
            <Name>João Silva</Name>
        </Owner>
    </Entry>
    <Reason>USER_REQUESTED</Reason>
    <RequestId>a946d533-7f22-42a5-9a9b-e87cd55c0f4d</RequestId>
</CreateEntryRequest>
```

**Response (201 Created):**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateEntryResponse>
    <Signature></Signature>
    <ResponseTime>2020-01-10T10:00:00.000Z</ResponseTime>
    <CorrelationId>a9f13566e19f5ca51329479a5bae60c5</CorrelationId>
    <Entry>
        <Key>+5561988880000</Key>
        <KeyType>PHONE</KeyType>
        <Account>
            <Participant>12345678</Participant>
            <Branch>0001</Branch>
            <AccountNumber>0007654321</AccountNumber>
            <AccountType>CACC</AccountType>
            <OpeningDate>2010-01-10T03:00:00.000Z</OpeningDate>
        </Account>
        <Owner>
            <Type>NATURAL_PERSON</Type>
            <TaxIdNumber>11122233300</TaxIdNumber>
            <Name>João Silva</Name>
        </Owner>
        <CreationDate>2019-11-18T03:00:00.000Z</CreationDate>
        <KeyOwnershipDate>2019-11-18T03:00:00.000Z</KeyOwnershipDate>
    </Entry>
</CreateEntryResponse>
```

**Typical errors (all 400 unless noted):**
- `EntryInvalid` -- invalid fields
- `EntryAlreadyExists` -- same key, participant and owner already registered
- `EntryKeyOwnedByDifferentPerson` -- key belongs to another person; an ownership claim is the way forward
- `EntryKeyInCustodyOfDifferentParticipant` -- same owner, other PSP; a portability claim is the way forward
- `EntryLimitExceeded` -- too many keys for the account
- `RequestIdAlreadyUsed`, `RequestSignatureInvalid`, `TaxIdNumberBlocked`
- `Forbidden` (403), `ResourceConflict` (409), `ServiceUnavailable` (503)

### getEntry

Looks up a key and returns the account and owner needed to build the pacs.008.

**Endpoint:** `GET /api/v2/entries/{Key}` (URL-encode the key; e.g. `+` in phones becomes `%2B`)

**Headers (all mandatory, used for rate limiting):**
- `PI-RequestingParticipant` -- ISPB of the direct or indirect participant making the query, or the first 8 digits of the CNPJ for payment initiators
- `PI-PayerId` -- CPF or CNPJ (digits only) of the payer
- `PI-EndToEndId` -- the `EndToEndId` of the payment this lookup is for (same value that goes in the pacs.008)

**Query:** `IncludeStatistics=true` adds anti-fraud counters (`OwnerStatistics`, `KeyStatistics`).

Responses may be cached following `Cache-Control`.

**Response (200):**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<GetEntryResponse>
    <Signature></Signature>
    <ResponseTime>2020-01-10T10:00:00Z</ResponseTime>
    <CorrelationId>a9f13566e19f5ca51329479a5bae60c5</CorrelationId>
    <Entry>
        <Key>11122233300</Key>
        <KeyType>CPF</KeyType>
        <Account>
            <Participant>12345678</Participant>
            <Branch>0001</Branch>
            <AccountNumber>0007654321</AccountNumber>
            <AccountType>CACC</AccountType>
            <OpeningDate>2010-01-10T03:00:00Z</OpeningDate>
        </Account>
        <Owner>
            <Type>NATURAL_PERSON</Type>
            <TaxIdNumber>11122233300</TaxIdNumber>
            <Name>João Silva</Name>
        </Owner>
        <CreationDate>2019-11-18T03:00:00Z</CreationDate>
        <KeyOwnershipDate>2019-11-18T03:00:00Z</KeyOwnershipDate>
        <OpenClaimCreationDate>2019-11-19T03:00:00Z</OpenClaimCreationDate>
    </Entry>
</GetEntryResponse>
```

**Errors:**
- `NotFound` (404) -- no entry for the key (costs 20 tokens in the user anti-scan bucket and 3 in the participant bucket)
- `EntryCannotBeQueriedForBookTransfer` (400) -- the key is held by the same PSP as the payer; do not query the DICT for internal transfers
- `EntryBlocked` (400) -- entry blocked by court order
- `EntryWithFraudRelatedRestriction` (400)
- `RateLimited` (429)

### updateEntry

Updates the account data, name or trade name of an entry that stays at the same PSP. Anything else (owner, PSP) requires delete + create, portability or an ownership claim.

**Endpoint:** `PUT /api/v2/entries/{Key}`, body `UpdateEntryRequest` (`Key`, `Account`, `Owner`, `Reason`).

Allowed reasons: EVP keys `BRANCH_TRANSFER`, `RECONCILIATION`, `RFB_VALIDATION`; other keys also `USER_REQUESTED`.

---

### deleteEntry

Removes a key. Only the PSP that holds the entry can delete it. Valid reasons: `USER_REQUESTED`, `ACCOUNT_CLOSURE`, `RECONCILIATION`, `FRAUD`, `RFB_VALIDATION`.

**Endpoint:** `POST /api/v2/entries/{Key}/delete` (there is no HTTP `DELETE`)

**Request:**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<DeleteEntryRequest>
    <Signature></Signature>
    <Key>+5561988887777</Key>
    <Participant>12345678</Participant>
    <Reason>ACCOUNT_CLOSURE</Reason>
</DeleteEntryRequest>
```

**Response (200):**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<DeleteEntryResponse>
    <Signature></Signature>
    <ResponseTime>2020-01-10T10:00:00.000Z</ResponseTime>
    <CorrelationId>a9f13566e19f5ca51329479a5bae60c5</CorrelationId>
    <Key>+5561988887777</Key>
</DeleteEntryResponse>
```

**Errors:** `NotFound` (404), `Forbidden` (403), `EntryLockedByClaim` (400, a claim that is not completed or cancelled exists for the key).

### createClaim

Starts a portability claim (same owner, key moves to another PSP) or an ownership claim (another person claims the key). Created by the claimer PSP at the end user's request. The current entry is unchanged until the donor confirms.

- Portability: CPF, CNPJ, PHONE, EMAIL.
- Ownership: PHONE only (per the claim matrix in the API spec).
- EVP: cannot be claimed.

**Endpoint:** `POST /api/v2/claims/`

**Request:**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateClaimRequest>
    <Signature></Signature>
    <Claim>
        <Type>OWNERSHIP</Type>
        <Key>+5561988887777</Key>
        <KeyType>PHONE</KeyType>
        <ClaimerAccount>
            <Participant>12345678</Participant>
            <Branch>0001</Branch>
            <AccountNumber>0007654321</AccountNumber>
            <AccountType>CACC</AccountType>
            <OpeningDate>2010-01-10T03:00:00Z</OpeningDate>
        </ClaimerAccount>
        <Claimer>
            <Type>NATURAL_PERSON</Type>
            <TaxIdNumber>11122233300</TaxIdNumber>
            <Name>João Silva</Name>
        </Claimer>
    </Claim>
</CreateClaimRequest>
```

**Response (201):**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateClaimResponse>
    <Signature></Signature>
    <ResponseTime>2020-01-10T10:00:00.000Z</ResponseTime>
    <CorrelationId>a9f13566e19f5ca51329479a5bae60c5</CorrelationId>
    <Claim>
        <Type>OWNERSHIP</Type>
        <Key>+5561988887777</Key>
        <KeyType>PHONE</KeyType>
        <ClaimerAccount>...</ClaimerAccount>
        <Claimer>...</Claimer>
        <DonorParticipant>87654321</DonorParticipant>
        <Id>123e4567-e89b-12d3-a456-426655440000</Id>
        <Status>OPEN</Status>
        <ResolutionPeriodEnd>2020-01-17T10:00:00.000Z</ResolutionPeriodEnd>
        <CompletionPeriodEnd>2020-01-17T10:00:00.000Z</CompletionPeriodEnd>
        <LastModified>2020-01-10T10:00:00.000Z</LastModified>
    </Claim>
</CreateClaimResponse>
```

**Errors:** `ClaimInvalid`, `ClaimTypeInconsistent` (ownership against an entry of the same person, or portability against an entry of another person), `ClaimAlreadyExistsForKey`, `ClaimResultingEntryAlreadyExists` (all 400); `ClaimKeyNotFound` (404).

**Claim lifecycle (`ClaimStatus`):**
1. `OPEN` -- created by the claimer
2. `WAITING_RESOLUTION` -- donor acknowledged it (`/acknowledge`)
3. `CONFIRMED` -- donor confirmed (`/confirm`); the donor's entry is removed
4. `COMPLETED` -- claimer completed it (`/complete`); the claimer's entry is created
5. `CANCELLED` -- cancelled by donor or claimer (`CancelledBy`)

**Periods:** the resolution period (`ResolutionPeriodEnd`) is 7 days for both types. Ownership claims also have a completion period (`CompletionPeriodEnd`), 7 more days, before the claimer can complete.

### acknowledgeClaim / confirmClaim / cancelClaim / completeClaim

| Operation | Path | Body | Who | Precondition |
|-----------|------|------|-----|--------------|
| acknowledge | `POST /claims/{ClaimId}/acknowledge` | `AcknowledgeClaimRequest`: `ClaimId`, `Participant` | Donor | `OPEN` |
| confirm | `POST /claims/{ClaimId}/confirm` | `ConfirmClaimRequest`: `ClaimId`, `Participant`, `Reason` | Donor only. Ownership: `USER_REQUESTED`, or `DEFAULT_OPERATION` after `ResolutionPeriodEnd`. Portability: `USER_REQUESTED`, `ACCOUNT_CLOSURE` | `WAITING_RESOLUTION` |
| cancel | `POST /claims/{ClaimId}/cancel` | `CancelClaimRequest`: `ClaimId`, `Participant`, `Reason` | Depends on type and reason (see spec) | `OPEN`, `WAITING_RESOLUTION` (ownership also `CONFIRMED`) |
| complete | `POST /claims/{ClaimId}/complete` | `CompleteClaimRequest`: `ClaimId`, `Participant`, `RequestId` | Claimer | `CONFIRMED` (ownership: after `CompletionPeriodEnd`) |

Reasons (`ClaimOperationReason`): `USER_REQUESTED`, `ACCOUNT_CLOSURE`, `FRAUD`, `DEFAULT_OPERATION`, `RECONCILIATION`, `RFB_VALIDATION` (`PARTICIPANT_EXCLUSION` is internal to the DICT).

Example (confirm):

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<ConfirmClaimRequest>
    <Signature></Signature>
    <ClaimId>123e4567-e89b-12d3-a456-426655440000</ClaimId>
    <Participant>12345678</Participant>
    <Reason>USER_REQUESTED</Reason>
</ConfirmClaimRequest>
```

The responses (`AcknowledgeClaimResponse`, `ConfirmClaimResponse`, `CancelClaimResponse`, `CompleteClaimResponse`) carry `ResponseTime`, `CorrelationId` and the full `Claim` with its new `Status`. Errors: `ClaimOperationInvalid`, `ClaimResolutionPeriodNotEnded`, `ClaimCompletionPeriodNotEnded` (400).

### createInfractionReport

Opens an infraction report on a settled SPI transaction (MED). `Reason` is `REFUND_REQUEST` (created by the **payer's** PSP of the original transaction) or `REFUND_CANCELLED` (created by the **receiver's** PSP). `SituationType`: `SCAM`, `ACCOUNT_TAKEOVER`, `COERCION`, `FRAUDULENT_ACCESS`, `OTHER` (then `ReportDetails` is mandatory), `UNKNOWN` (only for reports created in v1).

**Endpoint:** `POST /api/v2/infraction-reports/`

**Request:**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateInfractionReportRequest>
    <Signature></Signature>
    <Participant>99999010</Participant>
    <InfractionReport>
        <TransactionId>E9999901012341234123412345678900</TransactionId>
        <Reason>REFUND_REQUEST</Reason>
        <SituationType>SCAM</SituationType>
        <ReportDetails>Transação feita através de QR Code falso em boleto</ReportDetails>
        <ContactInformation>
            <Email>abc@pix.br</Email>
            <Phone>+5561988887777</Phone>
        </ContactInformation>
    </InfractionReport>
</CreateInfractionReportRequest>
```

**Response (201):** `CreateInfractionReportResponse` with the report plus `Id`, `Status` (`OPEN`), `ReporterParticipant`, `CounterpartyParticipant`, `CreationTime`, `LastModified`.

**Lifecycle (`InfractionReportStatus`):** `OPEN` → `ACKNOWLEDGED` (counterparty calls `/acknowledge`) → `CLOSED` (counterparty calls `/close` with `AnalysisResult` `AGREED` or `DISAGREED`). The reporter can `/cancel` it (`CANCELLED`).

**Errors (400):** `InfractionReportInvalid`, `InfractionReportTransactionNotFound`, `InfractionReportTransactionNotSettled`, `InfractionReportAlreadyBeingProcessedForTransaction`, `InfractionReportAlreadyProcessedForTransaction`, `InfractionReportPeriodExpired`, `InfractionReportOperationInvalid`.

### closeInfractionReport

Closed by the **counterparty** while the report is `ACKNOWLEDGED`. With `AGREED`, `FraudType` is mandatory (`APPLICATION_FRAUD`, `MULE_ACCOUNT`, `SCAMMER_ACCOUNT`, `OTHER`) and the DICT creates a fraud marker automatically (`FraudMarkerId` in the response).

**Endpoint:** `POST /api/v2/infraction-reports/{InfractionReportId}/close`

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CloseInfractionReportRequest>
    <Signature></Signature>
    <InfractionReportId>91d65e98-97c0-4b0f-b577-73625da1f9fc</InfractionReportId>
    <Participant>12345678</Participant>
    <FraudType>SCAMMER_ACCOUNT</FraudType>
    <AnalysisResult>AGREED</AnalysisResult>
    <AnalysisDetails>Valor bloqueado.</AnalysisDetails>
</CloseInfractionReportRequest>
```

### createRefund

Creates a refund request (solicitacao de devolucao). Only the **debited** participant (payer's PSP of the original transaction) can create it. `RefundReason`: `FRAUD`, `OPERATIONAL_FLAW` (then `RefundDetails` is mandatory), `PIX_AUTOMATICO` (`REFUND_CANCELLED` is deprecated). A `FRAUD` refund needs a matching infraction report (`RefundInfractionReportNotFound` otherwise).

**Endpoint:** `POST /api/v2/refunds/`

**Request:**

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CreateRefundRequest>
    <Signature></Signature>
    <Participant>99999010</Participant>
    <Refund>
        <TransactionId>E9999901012341234123412345678900</TransactionId>
        <RefundReason>FRAUD</RefundReason>
        <RefundAmount>100.00</RefundAmount>
        <RefundDetails>Houve fraude confirmada na transação.</RefundDetails>
    </Refund>
</CreateRefundRequest>
```

**Response (201):** `CreateRefundResponse` with the refund plus `Id`, `Status` (`OPEN`), `RequestingParticipant`, `ContestedParticipant`, `RefundAccount`, `MonitorAccount`, `CreationTime`, `LastModified`.

**Errors (400):** `RefundInvalid`, `RefundTransactionNotFound`, `RefundTransactionNotSettled`, `RefundAlreadyProcessedForTransaction`, `RefundAlreadyBeingProcessedForTransaction`, `RefundPeriodExpired`, `TransactionNotRefundable`, `RefundInfractionReportNotFound`, `RefundOperationInvalid`.

**Lifecycle (`RefundStatus`):** `OPEN` → `CLOSED` (by the contested participant) or `CANCELLED` (by the requester, only before it is closed).

### closeRefund

Closed by the **contested** participant while `OPEN`. `RefundAnalysisResult`: `TOTALLY_ACCEPTED`, `PARTIALLY_ACCEPTED`, `REJECTED`. On rejection, `RefundRejectionReason`: `NO_BALANCE`, `ACCOUNT_CLOSURE`, `INVALID_REQUEST` (only for `OPERATIONAL_FLAW`), `OTHER`. `RefundTransactionId` is the `RtrId` (`D...`) of the pacs.004 that returned the money.

**Endpoint:** `POST /api/v2/refunds/{RefundId}/close`

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CloseRefundRequest>
    <Signature></Signature>
    <RefundId>91d65e98-97c0-4b0f-b577-73625da1f9fc</RefundId>
    <Participant>12345678</Participant>
    <RefundAnalysisResult>TOTALLY_ACCEPTED</RefundAnalysisResult>
    <RefundAnalysisDetails>Valor totalmente estornado ao demandante.</RefundAnalysisDetails>
    <RefundTransactionId>D9999901012341234123412345678900</RefundTransactionId>
</CloseRefundRequest>
```

## Keeping in Sync: Lists, Events and Reconciliation

The DICT does not push notifications. Each PSP polls:

- **Claims:** `GET /claims/?Participant={ISPB}&IsDonor=true&Status=OPEN&ModifiedAfter=...` (and `IsClaimer=true` for your own claims). Results are ordered by `LastModified`; `HasMoreElements` tells you to fetch again. Walking closed time windows can return repeated items.
- **Infraction reports:** `GET /infraction-reports/?Participant={ISPB}&IsCounterparty=true&Status=OPEN&ModifiedAfter=...`
- **Refunds:** `GET /refunds/?Participant={ISPB}&ParticipantRole=...&Status=OPEN` (paginated with `Cursor` / `NextCursor`)
- **Event notifications:** `GET /event-notifications?Participant={ISPB}` (cursor-paginated, up to 200 per page, 7-day window). In 2.12.1 the event types are funds-recovery events only (`FUNDS_RECOVERY_ANALYSED`, `FUNDS_RECOVERY_COMPLETED`, `FUNDS_RECOVERY_INFORMATION_UPDATED`, `FUNDS_RECOVERY_CANCELLED`).
- **Entry reconciliation:** each entry has a CID. Use `POST /sync-verifications/` (per key type) to check whether your CID set matches the DICT's, `GET /cids/events` (`ADDED` / `REMOVED`) to follow changes, `POST /cids/files/` + `GET /cids/files/{Id}` for a full CID file, and `GET /cids/entries/{Cid}` to fetch one entry.

Polling lists costs tokens (see rate limits below: e.g. `CLAIMS_LIST_WITH_ROLE` 40/min).

## Rate Limits

Every operation is subject to a token-bucket policy. Exceeding one returns **429** (`RateLimited`). Check your buckets with `GET /policies/` and `GET /policies/{policy}`.

### getEntry (anti-scan)

| Policy | Scope | Applies to | 200 | 404 | Payment sent |
|--------|-------|------------|-----|-----|--------------|
| `ENTRIES_READ_USER_ANTISCAN` | End user (`PI-PayerId`) | EMAIL, PHONE keys | -1 | -20 | +1 PF / +2 PJ |
| `ENTRIES_READ_USER_ANTISCAN_V2` | End user | CPF, CNPJ, EVP keys | -1 | -20 | +1 PF / +2 PJ |
| `ENTRIES_READ_PARTICIPANT_ANTISCAN` | PSP | all key types | -1 | -3 | +1 |

User buckets: **PF 2/min, bucket 100; PJ 20/min, bucket 1,000.**

Participant buckets (`ENTRIES_READ_PARTICIPANT_ANTISCAN`, also used by `ENTRIES_STATISTICS_READ`) depend on the participant's category:

| Category | Refill | Bucket |
|----------|--------|--------|
| A | 25,000/min | 50,000 |
| B | 20,000/min | 40,000 |
| C | 15,000/min | 30,000 |
| D | 8,000/min | 16,000 |
| E | 2,500/min | 5,000 |
| F | 250/min | 500 |
| G | 25/min | 250 |
| H | 2/min | 50 |

### Other policies (any status except 500 costs 1 token)

| Policy | Operations | Refill | Bucket |
|--------|-----------|--------|--------|
| `ENTRIES_WRITE` | createEntry, deleteEntry | 1,200/min | 36,000 |
| `ENTRIES_UPDATE` | updateEntry | 600/min | 600 |
| `KEYS_CHECK` | checkKeys | 70/min | 70 |
| `CLAIMS_READ` | getClaim | 600/min | 18,000 |
| `CLAIMS_WRITE` | create/acknowledge/cancel/confirm/completeClaim | 1,200/min | 36,000 |

## Error Response Format

Errors follow RFC 7807 in XML (`application/problem+xml`). `type` is `https://dict.pi.rsfn.net.br/api/v2/error/<Type>`.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<problem xmlns="urn:ietf:rfc:7807">
  <type>https://dict.pi.rsfn.net.br/api/v2/error/NotFound</type>
  <title>Not found</title>
  <status>404</status>
  <detail>Entry associated with given key does not exist</detail>
</problem>
```

Validation errors may include a `violations` list.

### General error types

| Type | Status | Meaning |
|------|--------|---------|
| `BadRequest` | 400 | Malformed request |
| `Forbidden` | 403 | Authenticated participant violates an authorization rule |
| `NotFound` | 404 | Entity not found |
| `ResourceConflict` | 409 | Resource is being processed by another operation; retry shortly |
| `Gone` | 410 | Resource no longer available |
| `DeprecatedResource` | 410 | Resource deprecated |
| `RateLimited` | 429 | Rate limit reached |
| `InternalServerError` | 500 | Unexpected condition |
| `ServiceUnavailable` | 503 | Service unavailable (maintenance or outside the operating window) |

Business errors (`EntryInvalid`, `ClaimOperationInvalid`, `RefundInvalid`, ...) are listed with each operation above and are all **400**, except `ClaimKeyNotFound` (404). Other general 400 types: `RequestSignatureInvalid`, `RequestIdAlreadyUsed`, `InvalidReason`, `ParticipantInvalid`, `TaxIdNumberBlocked`, `UserOrAccountWithFraudRelatedRestriction`.
