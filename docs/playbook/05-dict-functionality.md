# 05 - DICT Functionality Testing

## Overview

DICT (Diretorio de Identificadores de Contas Transacionais) is the centralized key directory for Pix. It maps Pix keys (aliases) to bank account details, enabling instant payments without the payer needing to know the recipient's full banking information.

As a Direct Participant, you must implement and test all DICT operations: key lifecycle management, claims (portability and ownership), infraction reports, and refund solicitations. The DICT functionality test is scheduled separately from DICT capacity testing, and typically precedes it.

**Bacen virtual DICT participant:** earlier versions of this guide named ISPB `99999060` as the counterparty Bacen uses in the formal DICT tests. That ISPB does **not** appear in any official document we could check (the SPI Roteiro only names `99999A03` and `99999A04`, which are SPI virtual participants), so treat it as unverified and confirm the counterparty ISPB with Bacen when you schedule. During informal testing with partner PSPs, you will use each other's real ISPBs.

All paths below are relative to the DICT API v2 base: `https://dict-h.pi.rsfn.net.br:16522/api/v2/` in homologation (see [DICT API reference](../reference/dict-api.md)).

## Key Types

DICT supports five key types:

| Key Type | Format | Example | Notes |
|----------|--------|---------|-------|
| **CPF** | 11 digits | `12345678901` | Natural person tax ID |
| **CNPJ** | 14 digits | `12345678000195` | Legal entity tax ID |
| **EMAIL** | Standard email | `user@example.com` | Max 77 chars (limit for any key) |
| **PHONE** | E.164 format | `+5511999999999` | Must include country code |
| **EVP** | UUID v4 | `a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d` | Random key, generated by the DICT |

The number of keys per account is limited (the API returns `EntryLimitExceeded` when you exceed it). The limit is set by the Pix regulation, not the API spec; it is commonly cited as 5 keys per account for natural persons and 20 for legal entities.

## Key Lifecycle

### Create Key

Register a new key in DICT, binding it to an account at your PSP.

```
POST /api/v2/entries/
```

Signed `CreateEntryRequest` with `Entry` (`Key`, `KeyType`, `Account` with `Participant`, `Branch`, `AccountNumber`, `AccountType`, `OpeningDate`, and `Owner` with `Type`, `TaxIdNumber`, `Name`), `Reason` (`USER_REQUESTED` or `RECONCILIATION`) and `RequestId` (UUID v4, the idempotency key).

**Tips:**
- CNPJ and CPF documents must be valid (pass checksum validation). Invalid documents will be rejected. Some partner PSPs also validate documents during testing, so use real-format test documents.
- For EVP keys, the DICT generates the UUID -- omit `<Key>`.
- Account types: `CACC` (current), `SVGS` (savings), `SLRY` (salary), `TRAN` (payment account), `OTHR`.
- Retrying with the same `RequestId` is safe; the same `RequestId` with different data returns `RequestIdAlreadyUsed`.

### Lookup Key

Query a key to retrieve the associated account details. This is the most common DICT operation -- every Pix payment initiated by key triggers a lookup.

```
GET /api/v2/entries/{Key}
PI-RequestingParticipant: {your ISPB}
PI-PayerId: {CPF/CNPJ of the payer, digits only}
PI-EndToEndId: {EndToEndId of the payment being prepared}
```

The key type is not part of the path. For example:
```
GET /api/v2/entries/user@example.com
GET /api/v2/entries/%2B5511999999999
GET /api/v2/entries/a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d
GET /api/v2/entries/12345678901
GET /api/v2/entries/12345678000195
```

The three `PI-*` headers are mandatory for every key type and feed the anti-scan rate limits. Lookups are not signed. The signed `GetEntryResponse` includes the `Entry` (account: participant ISPB, branch, account number, type, opening date; owner: type, tax id, name) needed to build the pacs.008. Querying a key your own PSP holds returns `EntryCannotBeQueriedForBookTransfer` -- internal transfers must not hit the DICT.

With the toolkit client (`DictClient` in `scripts/utils/http-client.ts`):

```typescript
const res = await dict.call("GET", `/entries/${encodeURIComponent(key)}`, undefined, {
  payerId, endToEndId, okStatus: [404],
});
```

### Update Key

Update the account details, name or trade name of an existing key that stays at the same PSP (e.g., when a customer changes their account number). Other changes require delete + create, portability or an ownership claim.

```
PUT /api/v2/entries/{Key}
```

`UpdateEntryRequest` with `Reason`: EVP keys accept `BRANCH_TRANSFER`, `RECONCILIATION`, `RFB_VALIDATION`; other keys also `USER_REQUESTED`.

### Delete Key

Remove a key from DICT. The key becomes available for re-registration.

```
POST /api/v2/entries/{Key}/delete
```

Signed `DeleteEntryRequest` with `Key`, `Participant` and `Reason` (`USER_REQUESTED`, `ACCOUNT_CLOSURE`, `RECONCILIATION`, `FRAUD`, `RFB_VALIDATION`). A key with an open claim cannot be deleted (`EntryLockedByClaim`).

## Claims: Portability and Ownership

Claims are the mechanism for transferring Pix keys between PSPs (portability) or between different people (ownership).

### Portability Claims

A portability claim moves a key from one PSP to another, for the **same** account holder (same CPF/CNPJ). This happens when a customer wants to move their Pix key to a new bank.

**Flow:**
1. **Claimer PSP** (the PSP that wants the key) creates a portability claim via `POST /api/v2/claims/` (status `OPEN`)
2. **Donor PSP** (the PSP that currently holds the key) finds it by polling `GET /api/v2/claims/?Participant={ISPB}&IsDonor=true`
3. Donor PSP **acknowledges** it (`POST /claims/{ClaimId}/acknowledge`, status `WAITING_RESOLUTION`) and asks its user
4. Donor PSP **confirms** (`/confirm`, status `CONFIRMED`, donor entry removed) or **cancels** (`/cancel`)
5. Claimer PSP **completes** it (`/complete`, status `COMPLETED`) and the key is now registered at the claimer PSP

**Portability works for CPF, CNPJ, EMAIL and PHONE** (not EVP).

### Ownership Claims

An ownership claim transfers a key to a **different** account holder (different CPF/CNPJ). This happens when someone is given a phone number that was previously registered as a Pix key by someone else.

**IMPORTANT:** Ownership claims only work for **PHONE** keys. This is in the claim-compatibility table of the `createClaim` operation in DICT API 2.12.1 (OWNERSHIP: PHONE only; PORTABILITY: CPF, CNPJ, PHONE, EMAIL; EVP: neither). Attempts to open an ownership claim for an EMAIL key fail.

This was also what teams saw in homologation:

> "So funciona com chave pix celular" (It only works with phone key)
> -- Victor Kobinski, Woovi team

**Ownership Claim Flow:**
1. **Claimer PSP** creates an ownership claim for a PHONE key
2. **Donor PSP** acknowledges the claim (`WAITING_RESOLUTION`)
3. Donor PSP confirms (`USER_REQUESTED`, or `DEFAULT_OPERATION` once the 7-day resolution period has ended without an answer from the current owner) or the claim is cancelled
4. After confirmation, the claimer completes the claim once the completion period (`CompletionPeriodEnd`, 7 more days for ownership) has ended, and the key transfers

### Claim Testing with Partner PSPs

During DICT functionality homologation, you need a partner PSP to test claims bilaterally. Each side must act as both claimer and donor.

**Test matrix for claims:**

| Scenario | Your Role | Partner Role |
|----------|-----------|-------------|
| Portability - EMAIL | Claimer | Donor (confirm) |
| Portability - EMAIL | Donor | Claimer |
| Portability - PHONE | Claimer | Donor (confirm) |
| Portability - PHONE | Donor | Claimer |
| Portability - CNPJ | Claimer | Donor (confirm) |
| Portability - CNPJ | Donor | Claimer |
| Portability - CPF | Claimer | Donor (confirm) |
| Portability - CPF | Donor | Claimer |
| Ownership - PHONE | Claimer | Donor (confirm) |
| Ownership - PHONE | Donor | Claimer |
| Portability - Cancel | Claimer (cancel) | Donor |
| Ownership - Cancel | Claimer (cancel) | Donor |

**Practical tips:**
- To test portability, both PSPs must create the same key (same holder document) on their respective sides before the claimer requests portability.
- The donor PSP needs to poll `GET /claims/` (as donor) to find new claims; there is no push.
- After a claim is completed, verify the key lookup returns the new PSP.
- Claims have a 7-day resolution period (`ResolutionPeriodEnd`); ownership claims add a 7-day completion period (`CompletionPeriodEnd`). During testing, process them as soon as they arrive.

## Infraction Reports (MED - Mecanismo Especial de Devolucao)

Infraction reports are the first step of the MED process for handling fraud and operational issues in Pix transactions.

### Reasons

| `Reason` | Created by | Use Case |
|----------|-----------|----------|
| `REFUND_REQUEST` | Payer's PSP of the original transaction | User reports a scam and wants the money back (MED) |
| `REFUND_CANCELLED` | Receiver's PSP of the original transaction | Cancel a refund |

`SituationType` describes the context: `SCAM`, `ACCOUNT_TAKEOVER`, `COERCION`, `FRAUDULENT_ACCESS`, `OTHER` (requires `ReportDetails`). `OPERATIONAL_FLAW` is a **refund** reason, not an infraction reason.

### Infraction Report Lifecycle

```
OPEN --> ACKNOWLEDGED --> CLOSED (AnalysisResult AGREED or DISAGREED)
   \--> CANCELLED (by the reporter)
```

1. **Reporter PSP** creates the infraction report for a settled transaction (`TransactionId` = its `EndToEndId`); status `OPEN`
2. **Counterparty PSP** finds it by polling `GET /infraction-reports/?Participant={ISPB}&IsCounterparty=true`
3. Counterparty PSP **acknowledges** it (`/acknowledge`, status `ACKNOWLEDGED`)
4. Counterparty PSP **closes** it (`/close`) with `AnalysisResult` `AGREED` (plus mandatory `FraudType`) or `DISAGREED`
5. The reporter may **cancel** it (`/cancel`) instead

### Creating an Infraction Report

```
POST /api/v2/infraction-reports/
```

The signed `CreateInfractionReportRequest` includes `Participant` and an `InfractionReport` with:
- `TransactionId`: the `EndToEndId` of the original Pix transaction
- `Reason`: `REFUND_REQUEST` or `REFUND_CANCELLED`
- `SituationType`: context of the fraud
- `ReportDetails`: free-text description (mandatory when `SituationType` is `OTHER`)
- `ContactInformation`: email and phone for follow-up

### Testing Infraction Reports

You must test all combinations:

| Scenario | Your Role | Action |
|----------|-----------|--------|
| Create infraction for a Pix you sent | Reporter | Create report |
| Receive infraction for a Pix you received | Counterparty | Acknowledge, close `AGREED` |
| Receive infraction for a Pix you received | Counterparty | Acknowledge, close `DISAGREED` |
| Create infraction, then cancel it | Reporter | Create, then cancel |

**Practical tip:** Before creating an infraction report, you need an actual Pix transaction between the two PSPs. Send a Pix to your partner PSP, then open the infraction report referencing that transaction's `endToEndId`.

Example from real testing:

```
E54811417202504031334a1BrRnjRAbY - infraction report closed AGREED
E54811417202504031336apTfJD1OH2C - infraction report closed DISAGREED
```

### Fraud Markers

When the counterparty closes an infraction report with `AnalysisResult: AGREED`, the DICT creates a **fraud marker** automatically (`FraudMarkerId` in the response, typed by the mandatory `FraudType`: `APPLICATION_FRAUD`, `MULE_ACCOUNT`, `SCAMMER_ACCOUNT` or `OTHER`). Fraud markers feed the anti-fraud statistics returned by `GET /entries/{Key}?IncludeStatistics=true`. Markers can also be created directly with `POST /fraud-markers/`.

## Refund Solicitations

Refund solicitations are the second step of the MED process. Only the **debited** participant (the payer's PSP of the original transaction) can create one (`POST /api/v2/refunds/`).

### Types (`RefundReason`)

| Type | Linked To | Description |
|------|-----------|-------------|
| `FRAUD` | Infraction report for the transaction (else `RefundInfractionReportNotFound`) | Refund after fraud (MED) |
| `OPERATIONAL_FLAW` | No infraction report needed; `RefundDetails` mandatory | Refund due to operational error |
| `PIX_AUTOMATICO` | -- | Pix Automatico refunds |

### Refund Solicitation Flow

```
OPEN --> CLOSED (TOTALLY_ACCEPTED, PARTIALLY_ACCEPTED or REJECTED)
   \--> CANCELLED (by the requester, only before it is closed)
```

For FRAUD refunds:
1. An infraction report for the transaction exists (typically closed `AGREED`)
2. Payer's PSP creates the refund solicitation for the transaction
3. Contested PSP (receiver's side) finds it by polling `GET /refunds/` and evaluates it
4. If it returns money, the contested PSP sends a pacs.004 and closes the refund with the pacs.004 `RtrId` in `RefundTransactionId`

For OPERATIONAL_FLAW refunds:
1. Can be created without a prior infraction report
2. The flow is otherwise the same

### Refund Amount Handling

When a refund solicitation arrives:
- If the debited account has sufficient balance, refund the full amount and close with `RefundAnalysisResult` `TOTALLY_ACCEPTED`
- If the account has partial balance, refund what is available and close with `PARTIALLY_ACCEPTED`
- If the account has zero balance, close with `REJECTED` and `RefundRejectionReason` `NO_BALANCE`; when `MonitorAccount` is true, the account must be monitored as described in section 17 of the Manual Operacional do DICT (the monitoring period is defined there, not in the API spec)

### Testing Refund Solicitations

| Scenario | Your Role | Action |
|----------|-----------|--------|
| Create refund solicitation (FRAUD) | Reporter | Create after accepted infraction |
| Create refund solicitation (OPERATIONAL_FLAW) | Reporter | Create standalone |
| Receive refund solicitation | Contested | Return funds (pacs.004), close `TOTALLY_ACCEPTED` |
| Receive refund solicitation | Contested | Close `REJECTED` |

**Practical tip:** The full MED flow for testing is:
1. PSP A sends Pix to PSP B
2. PSP A opens an infraction report (`REFUND_REQUEST`)
3. PSP B acknowledges and closes it `AGREED`
4. PSP A creates a refund solicitation (`FRAUD`)
5. PSP B sends the pacs.004 and closes the refund `TOTALLY_ACCEPTED`

## DICT Sync / Polling

The DICT does not push anything. Claims, infraction reports and refund solicitations addressed to you are found by polling the list endpoints:

```
GET /api/v2/claims/?Participant={yourISPB}&IsDonor=true&Status=OPEN&ModifiedAfter={UTC date-time}
GET /api/v2/infraction-reports/?Participant={yourISPB}&IsCounterparty=true&Status=OPEN
GET /api/v2/refunds/?Participant={yourISPB}&ParticipantRole=...&Status=OPEN
GET /api/v2/event-notifications?Participant={yourISPB}   (funds-recovery events)
```

- Poll periodically (e.g., every 30-60 seconds); lists are rate limited (`CLAIMS_LIST_WITH_ROLE` 40/min, bucket 200)
- If `HasMoreElements` is `true` (or a `NextCursor` is returned), fetch the next page right away
- Process each item and act on it (`/acknowledge` for claims and infraction reports)
- Reconcile your entries with the DICT via CIDs: `POST /sync-verifications/`, `GET /cids/events`, `POST /cids/files/`

Unlike ICOM (at most 6 read streams per participant), the DICT has no stream limit; what limits you are the token-bucket policies.

## Rate Limiting

DICT imposes token-bucket rate limits per operation (policy) and, for lookups, per end user. Exceeding a policy returns HTTP 429 (`RateLimited`). Mirror them on your side:

- Lookups: `ENTRIES_READ_USER_ANTISCAN` (EMAIL/PHONE) and `ENTRIES_READ_USER_ANTISCAN_V2` (CPF/CNPJ/EVP) per payer -- PF 2/min, bucket 100; PJ 20/min, bucket 1,000; a 404 costs 20 tokens. `ENTRIES_READ_PARTICIPANT_ANTISCAN` per PSP, by participant category A-H (a 404 costs 3).
- Writes: `ENTRIES_WRITE` 1,200/min (bucket 36,000), `CLAIMS_WRITE` 1,200/min, and so on
- Use Redis or similar to manage rate limit state
- Check the DICT's view of your buckets with `GET /api/v2/policies/`
- Full table in the [DICT API reference](../reference/dict-api.md#rate-limits)

## Common Issues and Solutions

### Ownership Claim Rejected for EMAIL Keys
**Cause:** Attempting an ownership claim for an EMAIL key.
**Solution:** Ownership claims only work for PHONE keys (claim table in DICT API 2.12.1). Use portability claims for EMAIL keys instead.

### Claims Not Arriving at Donor PSP
**Cause:** The donor is not polling `GET /claims/` (as donor) or not processing results quickly enough.
**Solution:** Verify your polling job is running and handling `HasMoreElements`. Check that you call `/acknowledge`. In practice, the claim status should move from `OPEN` to `WAITING_RESOLUTION` within about 30 seconds of the claimer creating it.

### Infraction Report Linked to Non-Existent Transaction
**Cause:** Using an `EndToEndId` that was not settled (e.g., a transaction rejected with AB03). The DICT answers `InfractionReportTransactionNotFound` or `InfractionReportTransactionNotSettled` (400).
**Solution:** Ensure the referenced transaction was settled (the SPI sent the pacs.002 with `ACSC`) before creating the infraction report.

### Rate Limit Errors (HTTP 429)
**Cause:** Exceeding DICT rate limits.
**Solution:** Implement token-bucket rate limiting. Space out requests. For capacity testing, this is expected and must be handled gracefully.

### CPF/CNPJ Keys Not Found in Lookups
**Cause:** CPF/CNPJ keys often require KYC validation. Partner PSPs may have stricter validation in their testing environments.
**Solution:** Coordinate with partner PSP to use documents that pass their KYC (e.g., documents starting with `0` may auto-approve in some testing setups). Prefer EMAIL and EVP keys for initial testing.

### "Bad Request" on Key Creation
**Cause:** Invalid document format, missing required fields (`EntryInvalid`), or the key already exists (`EntryAlreadyExists`, `EntryKeyOwnedByDifferentPerson`, `EntryKeyInCustodyOfDifferentParticipant`).
**Solution:** Validate CPF/CNPJ checksums. Ensure all required fields are present. Read the `type` of the RFC 7807 problem to tell these apart.
